DAY 2: Security/Infra Angle
======================================================================

Certificate Transparency changed the web. Before CT, a certificate authority could quietly issue a fraudulent certificate and nobody would know until the damage was done. After CT, every certificate goes into a public, append-only, independently auditable log. Browsers refuse certificates that aren't logged.

AI verification has the same problem today that SSL had before CT.

Your AI agent verifies an output. Where does that proof go? Into the platform's internal database. Nobody outside the platform can audit it. Nobody can prove it happened. Nobody can detect if the platform quietly changed its story.

We built a transparency log for AI verification receipts. Append-only. Merkle tree inclusion proofs. Signed checkpoints. Witness cosigning for split-view defense. Static tiles served via CDN so anyone can mirror the entire log.

The receipt goes in. The hash is public. The content stays private. The proof is permanent.

102 tests passing. SHA-256 domain-separated hashing. Ed25519 signatures. Boring cryptographic infrastructure. The kind of boring that keeps you safe.

DAY 3: Legal Angle
======================================================================

Every fake-citation scandal has the same question underneath it:

Did anyone check this before it went out?

The harder question:

Can you prove it?

A platform audit log says "we checked it." A signed verification receipt says what was checked, what failed, what was flagged, and whether the result was safe to file. It carries an Ed25519 signature that anyone can verify independently. It travels with the brief, not inside the platform that drafted it.

If the check happened, the receipt proves it. If it didn't, the absence of a receipt is its own answer.

The next fake-citation scandal will not be excused by "our platform said it checked." The court will ask for the receipt.

DAY 5: Developer Angle
======================================================================

Verify an AI receipt offline with one command.

pip install svr-verify
svr-verify receipt.svr.json

That's it. No API key. No account. No network call after install. The verifier checks the Ed25519 signature against the canonical serialization, validates 22 required fields, enforces the count invariant (checked = passed + failed + excluded), and returns VALID or INVALID.

For CI/CD:
svr-verify receipt.svr.json --quiet
Exit code 0 = valid. Exit code 1 = invalid.

For Python:
from svr_verify import verify
result = verify("receipt.svr.json")

The receipt carries a required field called verification_method. It tells you whether the engine used deterministic math, an LLM, a rule engine, or a human. That field is what makes receipts from different engines comparable without trusting either engine.

MIT licensed. Zero engine dependencies. The whole point is adoption.

DAY 6: Standards Angle
======================================================================

Why do AI agents need a vendor-neutral receipt format?

Because agents are crossing tool boundaries.

An agent in Platform A drafts a document. An agent in Platform B reviews it. An agent in Platform C files it. Each platform may verify its own step internally. But the verification from Platform A does not travel to Platform B. The proof dies at the boundary.

Now the human at the end of the chain holds a filed document and cannot independently confirm that any step was verified. Three platforms touched it. Zero portable receipts exist.

The Signed Verification Receipt (SVR) is an open standard that solves this. A JSON file, signed with Ed25519, carrying the full audit result. It travels with the work product. Any platform can issue one. Any person can verify one.

The receipt ID prefix is issuer-defined. SATYA receipts start with SATYA-. A Thomson Reuters receipt would start with TR-. A Harvey receipt would start with HARVEY-. The verifier accepts any prefix. The standard is genuinely neutral.

One format. Many issuers. The proof travels.

======================================================================
DAY 7: SATYA/SIGMA Moat Angle
======================================================================

Every signed verification receipt declares its verification_method. That field is required, not optional.

deterministic_algebraic: zero probabilistic components. Zero parameters. Same input, same result, every time. Replayable by anyone with the engine version and the inputs.

probabilistic_llm: a large language model is in the verification loop. Seventy billion parameters. Different run, potentially different result. Not independently replayable.

Both methods produce a signed receipt. Both receipts verify with the same tool. Both carry the same structural fields.

But the declared method is permanent. It is signed into the receipt. It cannot be changed after issuance without breaking the signature.

When a regulator asks for evidence of "reasonable care," when an insurer prices AI liability, when an auditor compares two verification approaches side by side, that field is what they read.

The receipt does not argue which method is better. It just declares which method was used. The market decides.

SATYA produces receipts in 18.6 ms. Zero parameters. Deterministic replay. Sheaf cohomology for structural contradiction detection. The receipts say so, permanently, on the record.
